# 时间线精度检查（2026-10-21）

## 原因

原生引擎只统计部分 item 类型的起止区间及工具调用包装区间。`ContextCompaction`、`Extension(kind=clock.sleep)`、`ImageView` 未被识别。推理和回复的 item 起止时间通常只覆盖可见内容输出，不能代表整个模型请求；一些活动在毫秒精度下起止时间相同。首 Token 耗时只报告本轮第一次输出，无法解释后续每次工具返回到模型输出的间隔。

## 改动

- 单独识别上下文压缩和主动等待，并补齐图片查看等工具活动。
- 如果活动缺少开始时间或起止时间相同，使用该活动明确报告的 `duration` / `durationMs` 回算开始时间；没有耗时就保留为时间点。
- 新增「响应间隔（原因未知）」：从用户消息、工具返回或前一模型输出端点，到下一模型事件开始。精确 item 边界优先于 response_item 完成时间点；明确活动、首 Token 等待始终优先于间隔。缺失返回的调用不推算结束时间，也不把这段时间补成响应间隔。
- 包装调用不重复计算内部命令、工具、压缩或主动等待；独立活动仍按墙钟时间合并重叠。
- 展示明确区间、响应间隔、未分类的汇总，以及零时长记录数和未识别类型。索引版本升级为 4，重建旧缓存。
- 修复 item_completed 自带开始时间时未移除 pending_items 的问题。

## 本地日志对照

使用改动前本地 Release 引擎取得基线，再对相同聊天和轮次执行新引擎。样本为 3 个聊天的 33 个已完成轮次，总时长 17,600.772 秒。选取最近聊天及包含压缩/主动等待事件的聊天，属于定向诊断样本，不代表全部聊天的分布。排除进行中的轮次，不将原始聊天、工具参数、路径或标识写入仓库。

| 分类 | 改动前 | 改动后 |
| --- | ---: | ---: |
| 日志明确区间 | 33.94% | 36.09% |
| 响应间隔（内部原因未知） | 未单独区分 | 62.40% |
| 无法定位阶段的时间 | 66.06% | 1.51% |

明确补回的上下文压缩为 378.414 秒。235.016 秒主动等待现在单独展示，其中原来已有工具包装覆盖的时间不会增加明确区间总量。样本中有 339 个零时长活动，支持的新增类型覆盖了全部 item 类型。

全部 33 轮总时长保持不变；每轮时间片段连续、不重复，分类总和等于总时长。聚合原始结果见 `comparison.json`。

**响应间隔仍不能细分为模型内部推理、请求构建、网络传输、服务排队或运行时调度。** 本次提升的是阶段定位和已有日志利用率，而非对这些内部原因的实测。进一步拆分需要模型请求开始、首 Token、流结束、重试、审批及调度等更细粒度 trace。

## 验证

15 项 Rust 测试通过，包含新增 10 项时间线测试；33 项 Swift Release 测试执行，32 项通过，1 项要求显式设置环境变量的编辑器性能基准按其默认条件跳过。Rust Clippy（全部 targets）、Rust 格式检查、改动 Swift 文件的格式检查及差异检查通过。原生应用重新构建、打包并验证签名；使用独立 bundle ID 的临时副本验证时间线、图例、汇总及统计限制的实际显示，随后关闭该副本。
